Third-party options, and whether depending on one is acceptable\n\n- **`oddlama/gentoo-install`** — MIT, 775 stars, `pushed_at: 2026-02-14`, actively maintained. Where the line actually falls\n\nCompare, honestly, what each existing applier hands to whom:\n\n| Applier | Block layer | Root population | Configuration |\n|---|---|---|---|\n| autoinstall / debian / kickstart / agama | native answer file | native | native |\n| nixos | `disko` (declarative, distro-native) | `nixos-install` | `configuration.nix` |\n| archinstall | archinstall JSON | archinstall | archinstall |\n| **alpine** | **generated `lis-prepare.sh`: `parted mklabel`, `mkpart`, `mdadm --create`, `pvcreate`/`vgcreate`/`lvcreate`, `mkfs.*`, mount** | `setup-disk -m sys \"$mnt\"` | `answers` + `lis-post.sh` |\n| **gentoo (proposed)** | **generated shell: same parted/mdadm/lvm/cryptsetup/mkfs/mount** | **`tar xpf stage3` + `arch-chroot`** | **`make.conf`, `/etc/portage/*`, `eselect profile`, `emerge`, `installkernel`, `grub-mkconfig`** |\n\nThe delta between Alpine and Gentoo is **exactly one cell**: Alpine has `setup-disk -m sys \"$mnt\"`, a first-party command that takes a prepared mountpoint and installs the system into it. Gentoo has no such command; the equivalent is `tar xpf` over a Gentoo-signed release artifact. That is the entire honest gap.\n\nThree ways to argue about that cell, and my read of each:\n1. **`tar` is not Gentoo's tool.** True, literally. But the stage3 *is* Gentoo's release artifact, its GPG/BLAKE2B/SHA512 verification is a first-party procedure (and `gemato` + `/usr/share/openpgp-keys/gentoo-release.asc` are on the ISO), and the Handbook prescribes the exact `tar` invocation. There is no plausible alternative that is *more* Gentoo — including Calamares, whose `downloadstage3` module does the same download-verify-untar in Python.\n2. **`emerge --root=/mnt/gentoo @system` from binpkgs would be \"portage does the install.\"** I did **not** verify this works and I'd expect it to be fragile (no baselayout skeleton, no `/etc` seeding, unsupported by any documentation I found). Do not build on it. Flagging it as explicitly unverified.\n3. **Catalyst does it in shell too.** `create-qcow2.sh` is Gentoo's own answer to \"put an installed Gentoo on a block device,\" and it is parted + mkfs + `cp -a` + chroot-grub + heredoc-fstab. If that is acceptable as Gentoo's method for producing official release images, generated shell doing the same thing is not a betrayal of the rule — it's an implementation of it.\n\nSo: **a lis2gentoo applier is, in the block-layer/unpack span, us writing an installer. I will not pretend otherwise.** But (a) that span is identical in width to the one lis2alpine already occupies and the project already accepted, (b) it is the span for which Gentoo *has no tool at all* and never has, and (c) the much larger post-chroot span — profile, USE, keywords, sets, binhost, dist-kernel, dracut, grub, init system — is genuinely \"generate declarative config, let the distro's tooling act on it,\" which is where most of the LIS document's surface area lives anyway.\n\n---\n\n## 7. Design consequences to carry into the next phase\n\nThings a lis2gentoo design must confront, that fall out of the above:\n\n- **Runtime.** This is the biggest practical risk, bigger than any correctness question. With `FEATURES=\"getbinpkg\"`, official binhost, and `sys-kernel/gentoo-kernel-bin`, a base install is download-bound, not compile-bound. But `mdadm`, `zfs`, `systemd-boot` are **not** on the binhost, and any non-default USE flag forces a local build. A document that asks for RAID or ZFS or a non-default USE will compile. The applier should probably `refuse` or loudly warn on intent that provably forces a large source build, and the e2e timeout will need to be well above the 2400 s default (`lis2nixos` already uses 3600).\n- **Fail-closed opportunities that are genuinely Gentoo-shaped.** `system.init: systemd|openrc` maps to *both* the stage3 flavor and the profile, and they must agree — a mismatch is a clean refusal. `target.arch` maps to the autobuild directory (`amd64`, `arm64`, plus `x32`; no riscv64 in `releases/amd64/autobuilds` — riscv is qemu-built). musl/hardened/llvm/no-multilib/split-usr stage3 variants exist and are natural `x-gentoo` territory. `desktop` maps to a profile subtree.\n- **Secrets.** Nothing here changes: LUKS key material stays on the seed, `luks_key_path` + `SEED_MOUNT` as today. The one Gentoo-specific trap is that generated `/etc/portage/*` files land in the target and are world-readable — a `registration`/proxy token must never be written into `make.conf`'s `http_proxy`/`GENTOO_MIRRORS` if it embeds credentials.\n- **Birth certificate.** `/var/lib/lis/system.lis.json` mode 0600 — trivially satisfied inside the chroot.\n- **Where the emitted artifacts should live.** By analogy with lis2alpine's `answers` + `lis-prepare.sh` + `lis-post.sh`, something like: `lis-prepare.sh` (block layer + stage3 fetch/verify/unpack + chroot mounts), a *directory* of real Gentoo config (`make.conf`, `package.use/lis`, `package.accept_keywords/lis`, `package.license/lis`, `binrepos.conf/gentoo.conf`, `sets/lis`, `fstab`), and `lis-chroot.sh` (`emerge-webrsync`, `eselect profile set`, `emerge @world`/`@lis`, `installkernel`, `dracut`, `grub-install`, `grub-mkconfig`, users, services). The middle artifact is the part that is honestly declarative and should be as large as possible; the two scripts should be as small as possible. That ratio is the design's actual quality metric.\n- **`storage.wipe: false`** — same warning lis2alpine emits, for the same reason.\n- Reuse `chroot_intents`, `system_commands`, `file_commands`, `uid_commands`, `sudoers_commands`, `registration_commands`, `enrollment_commands`, `boot_timeout_commands`, `driver_packages`, `security_packages`, `check_encryption_emitted`, `check_raid_consumers`, `resolve_mountpoints`, `role_fs`, `role_mountpoint`, `track`/`check_unread` from `/home/bresilla/lis/tools/appliers/lis_common.py` — none of this is Gentoo-specific work.\n\n---\n\n## 8. RECOMMENDATION\n\n**FEASIBLE WITH CAVEATS** — build it, but document the compromise in the applier docstring rather than dressing it up.\n\nWhy feasible:\n- The e2e path is **empirically verified**, not assumed: the minimal ISO boots to a passwordless root shell on `ttyS0` via `-kernel`/`-initrd`, ships Python 3 plus every block-layer tool the LIS storage model needs, and slots into `install_from_live_shell()` with no `bootstrap=` and no new harness machinery.\n- The **majority of the LIS document surface** (`software`, `mirror`, `proxy`, `drivers`, `desktop`, `system.init`, `boot.loader`, `system.*`) maps onto first-party declarative Gentoo config files — `make.conf`, `/etc/portage/*` drop-in dirs, profile selection, `binrepos.conf` — consumed by Gentoo's own `emerge`, `eselect`, `installkernel`, `dracut`, and `grub-mkconfig`. That is the project's bar, met.\n- Official binhost (19,688 verified binpkgs) + pre-built dist-kernel make an unattended install finish in bounded time.\n\nWhy \"with caveats\" and not plain \"feasible\":\n- **There is no Gentoo tool that populates a root filesystem.** The block layer, the stage3 unpack, the chroot setup, and fstab will be generated shell. Its conclusion stands: there is no Gentoo tool that populates a root filesystem, none is coming, and Gentoo's own release engineering (`catalyst/targets/support/create-qcow2.sh`) does parted+mkfs+copy+chroot in shell.\n\nBut \"alpine already does this\" is a weaker argument than the report makes it. Alpine hands the *system installation* to `setup-disk -m sys \"$mnt\"` — that command writes fstab, populates the root, and (in disk mode) installs the bootloader. Gentoo has no such handoff, so `lis2gentoo` owns strictly more than `lis2alpine`: block layer **+ root population + fstab**. That is a real widening of the precedent, and it must be argued for on its own merits rather than smuggled in.\n\n**Conditions that make it defensible. Treat these as requirements, not suggestions:**\n\n1. **Do not write a second partitioner.** Extract `lis2alpine.prepare_script()` into a shared, tested `tools/appliers/lis_storage.py` and have both appliers call it. One implementation, one bug surface, one place to fix a divergence. This is the condition; without it I would recommend against building `lis2gentoo` at all.\n2. **Use the third-party-but-Gentoo-packaged tools that are already on the ISO instead of writing their equivalents.** `arch-chroot` for the chroot mounts (not a hand-rolled `mount --rbind` loop). **`genfstab -U /mnt/gentoo` for fstab** — never a generated heredoc. `gemato openpgp-verify-detached` + `/usr/share/openpgp-keys/gentoo-release.asc` for stage3 verification — never a hand-rolled `gpg --verify`. Each of these removes a class of silent divergence from our code.\n3. **Push everything possible into `/etc/portage/`.** The design's quality metric, as the report says, is the ratio between the emitted `/etc/portage/` tree and the emitted shell. Anything that can be a file must be a file.\n4. **The docstring says where the line falls**, in the same register as the report's §6 — not a defence, a statement.\n\n## 2. RISKS (ranked; silent-wrongness first)\n\n1. **A second hand-written partitioner diverging from alpine's.** Highest-probability source of a silently-wrong install, and the one this project has already been bitten by repeatedly. Mitigation is the shared `lis_storage.py` module, extracted *before* `lis2gentoo` is written, with a golden test: run `lis2alpine` over all eight examples before and after the extraction and require byte-identical `lis-prepare.sh`.\n2. **Binhost fallback to source.** If `getuto` has not seeded the trust store, or `binpkg-request-signature` is set without it, `emerge --getbinpkg` does not fail — it *silently compiles from source*. The run looks like a hang, and if the timeout is generous it looks like a slow success with a differently-built system. The live-shell route is useful and is us writing an installer with no cover at all. Do not blur them.**\n\nThe Void report is good on VAI's existence and shipped-vs-master drift — extracting `01-install.sh` from the real initrd was the right move and is the report's most valuable contribution. But it never asks the question that decides the project: *what does a VAI-scoped applier actually install?* The answer (Fact A above) is: nothing in this repository. All eight bundled recipes are refused. The first VM run would test the refusal path and nothing else.\n\nSo the verdict is a fork, and a maintainer has to pick before an engineer starts:\n\n- **Route V (VAI-scoped).** Genuinely native — official Void code, in every ISO, cmdline-triggered, sourced answer file, plus the documented `end_function` hook. Same category as `setup-alpine -f answers`. Cost: one new narrow recipe, and a MATRIX column that is mostly ⛔. Value: a real, defensible eighth applier and a working demonstration that fail-closed refusal is the correct outcome for an installer with a small envelope. **This is what I recommend building.**\n- **Route L (live shell + `xbps-install -r`).** Full LIS surface. `xbps-install -S -R $REPO -r /mnt base-system` has exactly the standing of `pacstrap`/`debootstrap`, and `xgenfstab`/`xchroot` are Void's own. But Void ships **no** declarative disk tool and **no** `setup-disk` equivalent, so the storage layer is 100% ours with no handoff at the end. That is a bigger step than Gentoo, where at least the post-chroot majority is native declarative config.\n\n**My recommendation:** Route V now. Revisit Route L only *after* `lis_storage.py` exists and has been exercised by both alpine and gentoo — at which point Route L costs one applier's worth of glue instead of a third partitioner, and the \"we wrote an installer\" objection is amortised rather than incurred a third time. Under no circumstances build one applier that silently picks between V and L per document: that is two behaviours behind one MATRIX column, which is precisely the class of lie MATRIX exists to prevent.\n\nThe rest of Part 2 assumes Route V.\n\n## 2.
